## Accepted Scope

The user approved the first-version frontend module, scenario validation,
documentation, and local installation. A real business-page trial requires
separate confirmation. Push, publication, deployment, and additional destructive
cleanup were outside this delivery.

The package adds one `frontend-governance` Skill, discovery metadata, and one
conditionally read delivery-checks reference. The lifecycle adds only the
scenario route. Existing modules retain goal and authority decisions, source
selection, falsifier design, and reporting; project and tool Skills retain
implementation, design, and browser mechanics. No state engine, runtime helper,
browser dependency, framework preference, fixed task form, or compulsory Plan
was added.

## Source Learning And Contract

The motivating report described Demo functionality drifting and development
narration appearing in product screens. Primary Skill documents were examined
on 2026-10-12 as method references, not installed dependencies:

- [better-codex](https://github.com/noobnooc/agent/blob/main/skills/better-codex/SKILL.md)
  supplied the separation of functional behavior and product-facing content.
- [Frontend Testing Debugging](https://github.com/openai/plugins/blob/main/plugins/build-web-apps/skills/frontend-testing-debugging/SKILL.md)
  supplied observable flow and rendered evidence methods; its one-interaction
  minimum does not establish every required flow of a delivery.
- [URL To Code](https://github.com/openai/plugins/blob/main/plugins/product-design/skills/url-to-code/SKILL.md)
  supplied reference capture and interaction comparison, within its frontend-only
  clone boundary.

The module connects reference applicability, promised delivery level, required
actions and actual effects, product copy, and scoped acceptance. Screenshots do
not establish hidden behavior; simulated state does not redefine business
contracts. Removing a development note and completing its missing function are
separate obligations. Copy decisions preserve useful help, errors, onboarding,
and truthful sample labels rather than applying a keyword blacklist.

Acceptance covers required behavior promised or affected by the slice and its
critical adjacent consumers. Builds, screenshots, interactions, mocks, and real
integration establish different claims. Missing access remains unverified;
explicitly approved visual or local prototypes retain their own boundaries.
Small changes remain small, and compatible current evidence can be reused.
